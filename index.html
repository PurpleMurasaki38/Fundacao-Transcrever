# 1. INTRODUÇÃO E OBJETIVOS

Este manual ensina a instalar, executar, verificar, personalizar e manter um ambiente de ferramentas de segurança baseado no HexStrike AI, utilizando Kali Linux e um projeto adicional chamado AXIOM.

O objetivo é compreender como as partes do ambiente se relacionam, sem depender de comandos aleatórios que podem falhar ou apagar configurações importantes.

Ao concluir os procedimentos, você deverá saber:

  • Localizar a pasta correta do projeto.
  • Instalar as dependências Python.
  • Criar e ativar um ambiente virtual.
  • Iniciar o servidor do HexStrike.
  • Verificar a resposta do servidor pela API.
  • Executar um teste simples com Nmap.
  • Identificar as ferramentas instaladas e as rotas disponíveis.
  • Investigar erros de conexão entre o HexStrike e o AXIOM.
  • Trocar arquivos do projeto por versões próprias.
  • Preservar cópias de segurança dos arquivos originais.
  • Reinstalar dependências quando um arquivo de requisitos for alterado.
  • Identificar se um erro está no servidor, na configuração, na dependência ou na ferramenta externa.

Regra principal: nunca substitua todos os arquivos de um projeto de uma só vez. Primeiro faça uma cópia de segurança, depois altere os arquivos necessários e teste o resultado.

Os nomes de pastas, portas e comandos deste manual correspondem ao ambiente de referência. Se uma versão diferente do programa utilizar outros caminhos, parâmetros ou portas, confirme a configuração local antes de executar os comandos.

# 2. O QUE É O HEXSTRIKE AI

O HexStrike AI é um projeto que integra ferramentas de segurança a uma interface de servidor e, em determinadas versões, a clientes compatíveis com o Model Context Protocol (MCP).

Dependendo da versão instalada e das dependências presentes no sistema, o projeto pode disponibilizar integrações com ferramentas para:

  • Reconhecimento de redes.
  • Identificação de serviços.
  • Análise de aplicações web.
  • Enumeração de ativos.
  • Análise de vulnerabilidades.
  • Auditoria de configurações.
  • Análise de arquivos.
  • Testes de segurança autorizados.

O HexStrike não substitui as ferramentas externas. Em muitos casos, ele funciona como uma camada de integração que recebe uma solicitação, verifica os parâmetros e executa uma ferramenta instalada no sistema.

Por isso, existem três componentes diferentes que precisam ser compreendidos:

1. O servidor HexStrike: recebe as requisições e coordena as operações.

2. As ferramentas externas: programas como Nmap, Hydra e outras ferramentas que precisam estar instaladas e disponíveis no sistema.

3. O cliente ou painel: a interface utilizada para enviar solicitações ao servidor. Pode ser outro programa, um cliente MCP ou um projeto personalizado, como o AXIOM deste ambiente.

Ter o servidor funcionando não significa que todas as ferramentas estejam instaladas. Da mesma maneira, instalar uma ferramenta não significa que sua rota esteja implementada corretamente na versão do HexStrike utilizada.

Referência do projeto:
https://github.com/0x4m4/hexstrike-ai

Importante: o repositório acima é uma referência do projeto. A instalação local pode ser um fork ou uma versão modificada, portanto os arquivos locais têm prioridade na hora de identificar rotas, parâmetros e funcionalidades realmente existentes.

# 3. KALI LINUX, WSL E CAINE

## 3.1. Kali Linux

O Kali Linux é uma distribuição Linux voltada a testes de segurança, auditoria, análise forense e atividades relacionadas à segurança da informação.

No ambiente deste manual, o terminal apresentado é o Kali Linux e o projeto está localizado no diretório pessoal do usuário.

O caminho utilizado como referência é:

~/cerebrocaine/hexstrike-ai

O símbolo ~ representa o diretório pessoal do usuário atual.

Por exemplo, o caminho completo pode ser semelhante a:

/home/kali/cerebrocaine/hexstrike-ai

Entretanto, o caminho real depende do nome do usuário e da estrutura de diretórios.

## 3.2. WSL

O WSL permite executar distribuições Linux dentro do Windows.

Se o Kali estiver sendo executado pelo WSL, os arquivos internos do Linux e os arquivos do Windows podem estar em sistemas de diretórios diferentes.

Não confunda os seguintes locais:

  • ~/cerebrocaine/hexstrike-ai: pasta do projeto dentro do Linux.
  • /mnt/c/Users/...: normalmente, arquivos da unidade C: do Windows acessados pelo Linux.
  • ~/.venv: possível ambiente virtual localizado na pasta pessoal.

Antes de editar arquivos, confirme em qual sistema eles estão.

## 3.3. CAINE

CAINE é também o nome de uma distribuição Linux voltada principalmente à investigação e análise forense digital. Ela não é a mesma distribuição que o Kali Linux.

Se você estiver utilizando o CAINE verdadeiro, e não apenas usando esse nome para se referir ao seu conjunto de ferramentas, não presuma que todos os comandos de instalação do Kali funcionarão da mesma maneira.

O HexStrike pode depender de versões de Python, bibliotecas e ferramentas que variam conforme a distribuição.

Para descobrir a distribuição atual, execute:

cat /etc/os-release

Para conferir a arquitetura:

uname -m

Para verificar a versão do Python:

python3 --version

Registre essas informações antes de fazer grandes alterações.

find ~/cerebrocaine -maxdepth 4 \

# 5. INSTALAÇÃO DO HEXSTRIKE AI DO ZERO

Esta seção é para uma instalação nova. Se você já possui um HexStrike personalizado, não clone outra cópia por cima da sua instalação atual.

## 5.1. Criar uma pasta de projetos

Opcionalmente, organize seus projetos em um diretório específico:

mkdir -p ~/cerebrocaine
cd ~/cerebrocaine

## 5.2. Baixar o repositório

O comando git clone baixa uma cópia de um repositório Git.

Para instalar uma nova cópia do projeto de referência:

git clone https://github.com/0x4m4/hexstrike-ai.git hexstrike-ai-novo

Entre na pasta:

cd ~/cerebrocaine/hexstrike-ai-novo

Confirme o conteúdo:

ls -la

A nova pasta foi nomeada hexstrike-ai-novo para não sobrescrever sua pasta existente hexstrike-ai.

Não apague a versão antiga até verificar se a nova funciona e se seus arquivos personalizados foram preservados.

## 5.3. Criar um ambiente virtual

Dentro da pasta da nova instalação:

python3 -m venv .venv

O ambiente virtual cria uma área separada para instalar dependências Python.

Ative-o:

source .venv/bin/activate

Quando estiver ativo, o prompt geralmente mostrará algo semelhante a (.venv).

Atualize o instalador Python dentro desse ambiente:

python -m pip install --upgrade pip

## 5.4. Instalar as dependências

Confira se o projeto contém requirements.txt:

ls -l requirements.txt

Se existir, instale as dependências declaradas nele:

python -m pip install -r requirements.txt

Se ocorrer um erro, leia a mensagem completa. O erro pode indicar uma biblioteca incompatível, uma versão de Python não suportada, falta de compilador ou dependência do sistema.

Não instale todas as bibliotecas que encontrar na internet sem verificar se a versão do projeto realmente precisa delas.

## 5.5. Confirmar o ambiente virtual

Execute:

which python
python --version
python -m pip --version

Os caminhos do Python e do pip deverão apontar para o ambiente virtual ativo, quando a ativação tiver funcionado.

# 6. COMO TRABALHAR COM O AMBIENTE VIRTUAL PYTHON

Um ambiente virtual não é o próprio HexStrike. Ele é o local em que ficam as dependências Python da instalação.

Uma pasta pode utilizar nomes diferentes para o ambiente virtual, por exemplo:

  • .venv
  • venv
  • hexstrike-env
  • hexstrike_env

O nome não é universal. É necessário verificar qual existe na instalação.

## 6.1. O erro `.venv/bin/activate: No such file or directory`

Esse erro significa que o caminho fornecido não existe a partir do diretório atual.

No ambiente de referência, o comando abaixo falhou:

source .venv/bin/activate

Isso não prova que o ambiente virtual foi apagado. Ele pode estar na pasta pai, em outra pasta ou ainda não ter sido criado.

Primeiro, entre no projeto:

cd ~/cerebrocaine/hexstrike-ai

Liste os diretórios:

ls -la
ls -la ~/cerebrocaine

Procure ambientes virtuais conhecidos:

find ~/cerebrocaine -maxdepth 4 \
  -type f -path "*/bin/activate" 2>/dev/null

Se o resultado mostrar:

/home/SEU_USUARIO/cerebrocaine/.venv/bin/activate

então o ambiente virtual está na pasta pai do projeto.

Nesse caso, estando dentro de hexstrike-ai, o comando correspondente é:

source ../.venv/bin/activate

Se o resultado apontar para outro caminho, utilize o caminho encontrado.

Se nenhum ambiente virtual for encontrado, crie um apenas depois de confirmar a pasta correta e a existência dos arquivos necessários:

cd ~/cerebrocaine/hexstrike-ai
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

Esse último procedimento pressupõe que requirements.txt exista e pertença à versão que você deseja executar.

## 6.2. Como sair do ambiente virtual

Execute:

deactivate

Isso desativa o ambiente virtual da sessão atual. Não apaga seus arquivos.

# 7. COMO INICIAR O SERVIDOR HEXSTRIKE

O servidor deve ser iniciado na pasta que contém o arquivo Python correto.

Entre no projeto:

cd ~/cerebrocaine/hexstrike-ai

Ative o ambiente virtual correto. No ambiente de referência, se o ambiente estiver na pasta pai:

source ../.venv/bin/activate

Confirme que o arquivo principal existe:

ls -l hexstrike_server.py

Inicie o servidor:

python3 hexstrike_server.py

Se a versão instalada aceitar o modo de depuração, você também poderá utilizar:

python3 hexstrike_server.py --debug

Não use opções que a versão local não reconhece.

Quando o servidor iniciar, observe o endereço e a porta exibidos no terminal.

No ambiente de referência, a porta esperada é 8888, com o endereço local:

http://127.0.0.1:8888

Mantenha esse terminal aberto. Se você encerrar o processo do servidor, as requisições enviadas a ele deixarão de funcionar.

Para executar outros comandos, abra um segundo terminal.

# 8. COMO VERIFICAR SE O HEXSTRIKE ESTÁ FUNCIONANDO

Abra outro terminal e execute:

curl -sS --max-time 10 \
  http://127.0.0.1:8888/health

No ambiente de referência, esse endereço respondeu com informações de saúde do servidor.

A resposta pode conter dados como:

  • Versão do servidor.
  • Número de ferramentas disponíveis.
  • Número de ferramentas registradas.
  • Estado de componentes internos.

A estrutura exata da resposta depende da versão.

## 8.1. Interpretar os resultados

### Caso A: o servidor responde com JSON

Isso indica que o endpoint de saúde respondeu. É um bom sinal, mas não comprova que todas as ferramentas estejam instaladas ou funcionais.

### Caso B: conexão recusada

O servidor pode estar desligado, escutando em outra porta ou vinculado a outra interface de rede.

Confira se o processo está em execução e leia as mensagens do terminal onde ele foi iniciado.

### Caso C: tempo limite

Pode haver um processo travado, um problema de rede ou uma requisição que demora mais do que o limite especificado.

### Caso D: erro HTTP 404

A conexão chegou a um servidor, mas o caminho solicitado não foi encontrado naquela aplicação. Verifique a rota e a versão correta da API.

### Caso E: erro HTTP 500

A aplicação recebeu a solicitação, mas encontrou um erro interno. Consulte o terminal do servidor.

### Caso F: erro HTTP 503

O serviço consultado não conseguiu atender à requisição. Se o AXIOM apresentar 503, isso não significa automaticamente que o HexStrike esteja quebrado: pode haver um serviço dependente desligado ou uma configuração de conexão incorreta.

# 9. COMO EXECUTAR O PRIMEIRO TESTE

Um primeiro teste deve ser simples, previsível e realizado em um sistema que você controla.

O ambiente de referência executou uma solicitação Nmap contra o próprio endereço local, utilizando a rota:

/api/tools/nmap

Comando:

curl -sS -X POST \
  http://127.0.0.1:8888/api/tools/nmap \
  -H "Content-Type: application/json" \
  -d '{"target":"127.0.0.1","scan_type":"-sV","ports":"80,443"}'

O que cada parte faz:

  • curl: envia a solicitação HTTP.
  • -sS: reduz mensagens de progresso, mas preserva erros.
  • -X POST: utiliza o método HTTP POST.
  • -H "Content-Type: application/json": informa que o corpo contém JSON.
  • target: endereço a ser examinado.
  • scan_type: tipo de verificação solicitado.
  • ports: portas especificadas para o teste.

No ambiente de referência, a resposta indicou sucesso e código de retorno zero. As portas verificadas no endereço local apareceram fechadas naquele momento.

Os resultados podem mudar conforme os serviços que estejam executando na máquina.

Importante: o exemplo verifica somente o endereço local. Não o transforme em uma varredura de terceiros sem autorização.

# 10. COMO DESCOBRIR AS FERRAMENTAS DISPONÍVEIS

O número total de ferramentas anunciado por uma versão do HexStrike não é necessariamente igual ao número de ferramentas instaladas no sistema operacional.

Há pelo menos três estados distintos:

  1. Ferramenta prevista no código.
  2. Rota ou integração registrada no servidor.
  3. Executável externo instalado e funcional.

Uma ferramenta pode estar prevista no código, mas não possuir seu executável instalado.

## 10.1. Procurar ferramentas no sistema

Para verificar o Nmap:

command -v nmap
nmap --version

Para verificar o Hydra:

command -v hydra
hydra -h

Para verificar o Subfinder:

command -v subfinder

Se command -v não mostrar um caminho, o executável provavelmente não está disponível no PATH.

## 10.2. Procurar referências a uma ferramenta no código

Dentro do projeto:

cd ~/cerebrocaine/hexstrike-ai
grep -ni "hydra" hexstrike_server.py | head -30

Para Nmap:

grep -ni "nmap" hexstrike_server.py | head -30

Para AXIOM:

grep -Rni "axiom" . \
  --exclude-dir=.git \
  --exclude-dir=.venv 2>/dev/null | head -80

Esses comandos procuram referências textuais. Eles não garantem, sozinhos, que uma ferramenta esteja funcional.

## 10.3. Procurar as rotas HTTP

Para procurar definições de rotas no arquivo principal:

grep -nE \
  '@app\.(route|get|post|put|delete)' \
  hexstrike_server.py | head -100

O resultado depende da estrutura do código. Algumas aplicações registram rotas por funções auxiliares, blueprints ou outros mecanismos.

Se uma rota não aparecer nessa busca, não conclua imediatamente que ela não existe. Procure também o nome da ferramenta e a função responsável por executá-la.

# 11. COMO CHAMAR FERRAMENTAS PELA API

A API é a interface HTTP utilizada para enviar solicitações ao servidor.

No ambiente de referência, a rota Nmap aceita uma requisição POST com um objeto JSON.

Exemplo de formato:

curl -sS -X POST \
  http://127.0.0.1:8888/api/tools/nmap \
  -H "Content-Type: application/json" \
  -d '{"target":"127.0.0.1","scan_type":"-sV","ports":"80,443"}'

Não presuma que todas as rotas aceitam os mesmos campos.

Uma rota pode exigir:

  • Um alvo.
  • Uma lista de portas.
  • Um nome de arquivo.
  • Um tipo de análise.
  • Um diretório de saída.
  • Outros parâmetros específicos.

A maneira correta de descobrir os parâmetros aceitos é ler a função da rota no código da versão instalada.

## 11.1. Inspecionar uma rota

Primeiro, localize a definição:

grep -n -i "api/tools/nmap" hexstrike_server.py

Anote o número da linha retornado.

Em seguida, use sed para visualizar o trecho correspondente. Substitua os números do exemplo pelo intervalo encontrado:

sed -n '1000,1100p' hexstrike_server.py

Os números acima são apenas um exemplo de intervalo, não a localização garantida da rota.

Procure dentro da função:

  • O nome dos campos JSON.
  • Os valores obrigatórios.
  • A validação de entrada.
  • A forma como os argumentos são montados.
  • O tratamento de erros.
  • A resposta devolvida ao cliente.

Nunca invente campos JSON e espere que todas as rotas os aceitem. Uma rota pode simplesmente rejeitar a solicitação ou ignorar os campos desconhecidos.

Não instale uma lista enorme de ferramentas de uma só vez se você ainda não sabe quais são necessárias. Instale e teste por etapas para conseguir identificar a origem de um eventual erro.

# 13. COMO UTILIZAR O HYDRA EM UM LABORATÓRIO

O Hydra é uma ferramenta de auditoria de autenticação que pode testar combinações de credenciais em serviços compatíveis.

Seu uso precisa estar limitado a sistemas próprios, máquinas de laboratório ou alvos para os quais você tenha autorização explícita.

Um endereço público não se torna automaticamente um alvo autorizado só por estar relacionado a um site educativo.

## 13.1. Verificar a instalação

command -v hydra
hydra -h

Se o programa não estiver instalado, em uma distribuição compatível com os repositórios Debian:

sudo apt update
sudo apt install -y hydra

## 13.2. Entender a diferença entre Hydra e HexStrike

O Hydra é o executável que realiza os testes de autenticação.

O HexStrike é a camada de integração que pode disponibilizar uma rota para executar o Hydra, caso essa integração esteja presente na sua versão.

Para verificar se existe uma rota relacionada ao Hydra:

cd ~/cerebrocaine/hexstrike-ai
grep -ni "hydra" hexstrike_server.py | head -50

Se encontrar uma rota, leia a implementação para descobrir os parâmetros que ela realmente aceita.

Se não encontrar, procure em outros arquivos do projeto:

grep -Rni "hydra" . \
  --exclude-dir=.git \
  --exclude-dir=.venv 2>/dev/null | head -100

Uma ferramenta instalada no Kali não ganha automaticamente uma rota na API do HexStrike.

## 13.3. Prática responsável

Para aprender o funcionamento do Hydra, utilize uma aplicação de teste local criada por você ou um laboratório dedicado que autorize expressamente esse tipo de teste.

Antes de iniciar, confirme:

  • Qual máquina está autorizada.
  • Qual serviço será testado.
  • Quais credenciais de laboratório serão utilizadas.
  • Qual é o limite de tentativas permitido.
  • Se a atividade pode afetar a disponibilidade do serviço.

Não execute ataques de força bruta contra logins públicos de terceiros sem autorização específica.

# 14. O QUE É O AXIOM NESTE AMBIENTE

Neste manual, AXIOM é o nome do projeto adicional que você utiliza junto ao HexStrike.

O contexto de referência indica uma aplicação ou serviço local associado à porta 8890. Entretanto, o nome AXIOM é utilizado por diferentes programas, e não há informação suficiente aqui para garantir qual é o código exato ou a arquitetura interna do seu projeto.

Por isso, este manual trata o AXIOM como uma aplicação personalizada cuja pasta, comando de inicialização e arquivo de configuração precisam ser confirmados na instalação real.

Não confunda:

  • O servidor HexStrike, esperado na porta 8888.
  • O serviço AXIOM, associado à porta 8890.
  • Os arquivos e diretórios usados por cada projeto.
  • As dependências Python de cada aplicação.
  • O cliente que envia solicitações para essas aplicações.

Duas aplicações podem estar instaladas na mesma máquina e ainda assim não conseguir se comunicar.

# 15. COMO VERIFICAR E INICIAR O AXIOM

## 15.1. Verificar se a porta está respondendo

Execute:

curl -i --max-time 10 http://127.0.0.1:8890/

Esse comando consulta a raiz do servidor. Um erro 404 na raiz não prova que o servidor esteja desligado; a aplicação pode simplesmente não possuir uma rota /.

Se o projeto possuir uma rota de saúde documentada, consulte essa rota.

Não presuma que o AXIOM use /health só porque o HexStrike usa esse caminho.

## 15.2. Verificar o processo

Em sistemas que possuem ss, execute:

ss -ltnp | grep -E ':8888|:8890'

Esse comando ajuda a identificar se existem processos escutando nas portas esperadas.

Se nenhum processo estiver escutando em 8890, o serviço pode estar desligado, configurado em outra porta ou falhando antes de iniciar.

## 15.3. Encontrar os arquivos de inicialização

Entre na pasta que contém seus projetos:

cd ~/cerebrocaine
ls -la

Procure arquivos comuns de inicialização:

find . -maxdepth 4 -type f \
  \( -name "app.py" \
  -o -name "main.py" \
  -o -name "server.py" \
  -o -name "package.json" \
  -o -name "index.html" \
  -o -name "docker-compose.yml" \
  -o -name "compose.yaml" \) 2>/dev/null

Essa lista serve como ponto de partida. O arquivo real do AXIOM pode ter outro nome.

Procure referências à porta:

grep -Rni "8890" . \
  --exclude-dir=.git \
  --exclude-dir=.venv 2>/dev/null | head -100

Examine os arquivos encontrados antes de iniciar ou modificar o projeto.

## 15.4. Iniciar o AXIOM

O comando de inicialização precisa corresponder à tecnologia e à estrutura do seu projeto.

Exemplos possíveis, que não devem ser executados sem confirmar a existência do arquivo correspondente:

python3 app.py

ou:

python3 server.py

ou, para um projeto Node.js que tenha um script apropriado no package.json:

npm start

Esses exemplos não são comandos universais. O nome do arquivo e o script correto devem ser descobertos no seu AXIOM.

# 16. COMO CONECTAR O AXIOM AO HEXSTRIKE

Uma integração entre duas aplicações normalmente depende de quatro elementos:

  1. O servidor de origem está em execução.
  2. O endereço e a porta de destino estão corretos.
  3. O caminho HTTP utilizado existe.
  4. O formato da requisição é aceito pelo servidor de destino.

No ambiente de referência:

  • HexStrike: http://127.0.0.1:8888
  • AXIOM: http://127.0.0.1:8890

Esses endereços só funcionam dessa forma se os serviços estiverem na mesma máquina ou no mesmo contexto de rede.

## 16.1. Testar primeiro o HexStrike

curl -i --max-time 10 \
  http://127.0.0.1:8888/health

Se o HexStrike não responder, resolva esse problema antes de investigar a integração.

## 16.2. Testar o AXIOM

curl -i --max-time 10 \
  http://127.0.0.1:8890/

Registre o código HTTP e a resposta.

## 16.3. Investigar um erro 503

Se o AXIOM retornar 503 Service Unavailable, investigue:

  • Se o AXIOM está esperando que o HexStrike esteja ligado.
  • Se o AXIOM utiliza a porta correta.
  • Se o AXIOM chama uma rota realmente existente.
  • Se a requisição está chegando ao serviço esperado.
  • Se há uma mensagem de erro no terminal do AXIOM.
  • Se o HexStrike retornou um erro ao processar a solicitação.

O erro 503 não deve ser resolvido alterando portas aleatoriamente.

## 16.4. Ordem recomendada de inicialização

Para um sistema no qual o AXIOM depende do HexStrike:

  1. Inicie o ambiente Linux.
  2. Entre na pasta do HexStrike.
  3. Ative o ambiente virtual correto.
  4. Inicie o HexStrike.
  5. Confirme que /health responde.
  6. Abra outro terminal.
  7. Inicie o AXIOM usando o comando real do projeto.
  8. Teste o AXIOM.
  9. Faça uma requisição simples de integração.
  10. Examine os registros de ambos os serviços se houver falha.

Essa sequência facilita a identificação do componente responsável pelo erro.

# 17. COMO TROCAR OS ARQUIVOS DO PROJETO PELOS MEUS ARQUIVOS

Esta seção trata da substituição de arquivos próprios, versões modificadas, interfaces personalizadas e arquivos de configuração.

A regra fundamental é: faça backup, identifique o destino, substitua somente o que precisa ser substituído e teste antes de apagar a versão antiga.

## 17.1. Identificar a pasta correta

Para o HexStrike:

cd ~/cerebrocaine/hexstrike-ai
pwd
ls -la

Confirme que você está na pasta correta antes de continuar.

Se o arquivo que deseja substituir pertence ao AXIOM, não o copie para dentro do HexStrike sem confirmar que esse é realmente o destino esperado.

## 17.2. Criar uma pasta de backup

Crie uma pasta de cópias de segurança fora do diretório que será modificado:

mkdir -p ~/cerebrocaine/backups

Para copiar um arquivo antes de substituí-lo, use:

cp -a arquivo.py \
  ~/cerebrocaine/backups/arquivo.py.backup

Troque arquivo.py pelo nome verdadeiro do arquivo.

O comando cp -a preserva atributos que podem ser relevantes para a cópia.

## 17.3. Fazer uma cópia completa do projeto

Antes de alterações grandes, volte ao diretório que contém a pasta do projeto:

cd ~/cerebrocaine

Crie uma cópia do diretório:

cp -a hexstrike-ai hexstrike-ai-backup

Esse procedimento pode exigir espaço adicional no disco, especialmente se a pasta possuir grandes ambientes virtuais, caches ou arquivos baixados.

A cópia não atualiza nem sincroniza automaticamente os dois diretórios. É uma fotografia do conteúdo no momento da cópia.

## 17.4. Copiar um arquivo próprio para o projeto

Imagine que seu arquivo personalizado esteja em:

~/Downloads/hexstrike_server.py

E que você queira substituir o arquivo principal do projeto.

Primeiro, faça backup:

cd ~/cerebrocaine/hexstrike-ai

cp -a hexstrike_server.py \
  ~/cerebrocaine/backups/hexstrike_server.py.original

Depois, confirme a existência do arquivo de origem:

ls -l ~/Downloads/hexstrike_server.py

Se o arquivo for realmente o correto, copie-o:

cp ~/Downloads/hexstrike_server.py \
  ~/cerebrocaine/hexstrike-ai/hexstrike_server.py

Compare os arquivos:

diff -u \
  ~/cerebrocaine/backups/hexstrike_server.py.original \
  ~/cerebrocaine/hexstrike-ai/hexstrike_server.py

O diff mostra diferenças entre as versões.

Se a comparação revelar alterações inesperadas, restaure o backup antes de continuar.

## 17.5. Restaurar o arquivo original

Se a versão nova apresentar erros, restaure o backup:

cp -a \
  ~/cerebrocaine/backups/hexstrike_server.py.original \
  ~/cerebrocaine/hexstrike-ai/hexstrike_server.py

Esse comando substitui o arquivo atual pelo backup. Use-o somente quando tiver certeza de que o backup é a versão desejada.

## 17.6. Não substitua a pasta inteira sem planejamento

Evite copiar uma pasta completa de arquivos personalizados sobre o projeto sem verificar o conteúdo.

Isso pode substituir ou apagar:

  • Rotas existentes.
  • Funções que outras partes do código utilizam.
  • Arquivos de requisitos.
  • Configurações locais.
  • Scripts de inicialização.
  • Recursos do painel.
  • Arquivos de dados.
  • Ajustes de integração com o AXIOM.

Se você tiver uma versão própria do servidor, o melhor procedimento é comparar os arquivos e incorporar as alterações necessárias de forma controlada.

# 18. COMO SUBSTITUIR ARQUIVOS PYTHON SEM DESTRUIR O PROJETO

Arquivos .py podem conter rotas, funções, configurações e a lógica central da aplicação.

Antes de substituir um arquivo Python, verifique se o novo arquivo é compatível com a versão do restante do projeto.

## 18.1. Verificar a sintaxe

Depois de copiar o arquivo, execute:

python3 -m py_compile hexstrike_server.py

Se não houver mensagem de erro, a sintaxe básica foi aceita pelo compilador.

Isso não garante que todas as bibliotecas estejam instaladas nem que o servidor funcione corretamente.

## 18.2. Verificar os imports

Observe as linhas import e from ... import ... do arquivo.

Se o arquivo novo depender de uma biblioteca que não existe no ambiente, o programa pode falhar ao iniciar.

Com o ambiente virtual correto ativado, tente iniciar o servidor e observe o erro completo.

Não instale uma biblioteca só porque o nome apareceu em uma mensagem sem antes confirmar que ela pertence à versão que você deseja executar.

## 18.3. Preservar as rotas antigas

Se seu objetivo for adicionar uma nova ferramenta, talvez seja melhor adicionar uma rota nova do que substituir todo o arquivo hexstrike_server.py.

Antes de editar:

grep -nE \
  '@app\.(route|get|post|put|delete)' \
  hexstrike_server.py | head -100

Depois, procure a rota que deseja alterar e leia a função completa.

Uma rota depende da estrutura da aplicação. Copiar somente um trecho de código pode falhar se ele utilizar funções auxiliares, variáveis globais ou bibliotecas que não existem no arquivo de destino.

## 18.4. Testar depois da alteração

Após uma alteração:

  1. Faça uma verificação de sintaxe.
  2. Inicie o servidor.
  3. Leia o terminal.
  4. Consulte /health.
  5. Execute um teste local simples.
  6. Confirme que as rotas antigas continuam funcionando.
  7. Teste a nova função isoladamente.

Não faça cinco alterações diferentes de uma só vez. Se algo falhar, será muito mais difícil descobrir qual mudança causou o problema.

# 19. COMO SUBSTITUIR ARQUIVOS HTML, CSS E JAVASCRIPT

Se o AXIOM possuir uma interface web, os arquivos da interface podem ser diferentes dos arquivos do servidor.

Os tipos mais comuns são:

  • .html: estrutura da página.
  • .css: cores, fontes, tamanhos e layout.
  • .js: interações, chamadas HTTP e comportamento da interface.
  • .json: configurações ou dados estruturados.
  • .py: lógica do servidor, caso a aplicação utilize Python.

Antes de trocar um arquivo, descubra qual deles é realmente carregado pela aplicação.

## 19.1. Localizar arquivos web

Dentro da pasta do projeto:

find . -maxdepth 5 -type f \
  \( -name "*.html" \
  -o -name "*.css" \
  -o -name "*.js" \) \
  -not -path "*/.git/*" \
  -not -path "*/node_modules/*"

O resultado ajuda a localizar os recursos da interface.

## 19.2. Fazer backup

Exemplo para um arquivo HTML:

cp -a index.html \
  ~/cerebrocaine/backups/index.html.backup

Substitua index.html pelo caminho verdadeiro do arquivo.

## 19.3. Copiar a nova versão

Se o seu arquivo estiver em ~/Downloads/index.html:

cp ~/Downloads/index.html ./index.html

Esse comando pressupõe que você esteja no diretório correto e que o arquivo de destino deva realmente se chamar index.html.

Se o arquivo pertencer a uma pasta como static, templates, public ou src, use o caminho que a estrutura do projeto exigir.

## 19.4. Quando a interface não muda

Se o arquivo foi substituído, mas a página continua igual, verifique:

  • Se você alterou o arquivo correto.
  • Se a aplicação serve arquivos de outra pasta.
  • Se o servidor precisa ser reiniciado.
  • Se o navegador está usando arquivos em cache.
  • Se o projeto utiliza um processo de compilação.
  • Se o HTML carrega outro CSS ou JavaScript.
  • Se a interface é gerada dinamicamente pelo servidor.

Não altere o backend inteiro para corrigir um problema que pode estar apenas no navegador.

## 21.3. Não sobrescrever o repositório com uma versão aleatória

Um arquivo encontrado na internet pode pertencer a outra versão do programa.

Antes de utilizar um arquivo externo, confira:

  • De qual repositório ele veio.
  • Qual versão o acompanha.
  • Quais dependências ele exige.
  • Se as rotas correspondem à sua instalação.
  • Se os parâmetros são compatíveis.

# 23. COMO RESOLVER OS ERROS MAIS COMUNS

## Erro 1 — `.venv/bin/activate` não existe

Causa provável: o ambiente virtual está em outro caminho ou ainda não foi criado.

Diagnóstico:

cd ~/cerebrocaine/hexstrike-ai
ls -la
find ~/cerebrocaine -maxdepth 4 \
  -type f -path "*/bin/activate" 2>/dev/null

Use o caminho encontrado. Não crie um novo ambiente antes de verificar os existentes.

## Erro 2 — `python3: can't open file 'hexstrike_server.py'`

Causa provável: o terminal está no diretório errado ou o arquivo foi renomeado.

Diagnóstico:

pwd
ls -la
find ~/cerebrocaine -maxdepth 4 \
  -name "hexstrike_server.py" 2>/dev/null

Entre na pasta que realmente contém o arquivo.

## Erro 3 — `ModuleNotFoundError`

Causa provável: uma biblioteca Python não está instalada no ambiente utilizado.

Diagnóstico:

which python
python -m pip --version

Se houver um requirements.txt correto para essa versão:

python -m pip install -r requirements.txt

Depois, tente iniciar o programa novamente.

## Erro 4 — `Address already in use`

Causa provável: outro processo já está utilizando a porta.

Confira:

ss -ltnp | grep -E ':8888|:8890'

Identifique o processo antes de pará-lo. Não encerre processos desconhecidos sem entender sua função.

## Erro 5 — `/health` retorna 404

Causa provável: o servidor consultado não possui essa rota, ou você está acessando o programa ou a porta errada.

Confira o endereço e a implementação da rota. Não confunda um 404 com uma falha de conexão.

## Erro 6 — `/api/tools/status` retorna 404

Causa provável: essa rota não está implementada na versão instalada.

Não presuma que ela exista porque aparece em um tutorial de outra versão.

Procure no código as rotas que a instalação realmente implementa.

## Erro 7 — AXIOM retorna 503

Causa provável: o serviço não consegue atender à solicitação, possivelmente por depender de outro componente ou de uma configuração inválida.

Teste os dois serviços separadamente e consulte os registros de cada um.

## Erro 8 — A ferramenta não foi encontrada

Causa provável: o executável externo não está instalado ou não está disponível no PATH.

Confira:

command -v nome_da_ferramenta

Substitua nome_da_ferramenta pelo nome real do executável.

## Erro 9 — A API rejeita os parâmetros

Causa provável: os campos enviados não correspondem aos campos aceitos pela rota.

Leia a implementação da rota e utilize os nomes e formatos esperados.

## Erro 10 — O painel não mostra as alterações

Causa provável: o arquivo errado foi modificado, o servidor precisa ser reiniciado, o navegador usa cache ou existe uma etapa de compilação.

Localize os arquivos carregados pela aplicação e teste uma alteração pequena antes de substituir todo o painel.

# 25. COMO CONFIGURAR A INICIALIZAÇÃO AUTOMÁTICA

# 27. SEGURANÇA E LIMITES DE UTILIZAÇÃO

O HexStrike pode coordenar ferramentas que executam operações reais sobre redes, serviços e aplicações.

Por isso, utilize o ambiente com responsabilidade.

Boas práticas:

  • Testar primeiro em 127.0.0.1 ou em um laboratório próprio.
  • Obter autorização antes de examinar sistemas de terceiros.
  • Respeitar o escopo de programas de recompensa por vulnerabilidades.
  • Não realizar força bruta contra logins públicos sem autorização específica.
  • Não coletar credenciais de terceiros.
  • Não expor o servidor de ferramentas à internet sem necessidade.
  • Não compartilhar tokens e chaves de API.
  • Fazer backups antes de substituir arquivos.
  • Revisar os parâmetros antes de executar ferramentas.
  • Evitar executar scripts desconhecidos como administrador.
  • Manter registros das alterações e dos testes.

Uma interface de IA não elimina a necessidade de verificar o alvo, os parâmetros e os efeitos de cada operação.
